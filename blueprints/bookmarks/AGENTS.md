# Bookmarks blueprint

The runnable fullstack reference: an API server for one resource, `Bookmark`, and a React web app
that uses it. It shows each technical capability once. Copy its shapes when you build a real
service; its behaviour is [`specs/001-bookmarks-blueprint`](../../specs/001-bookmarks-blueprint/spec.md).
Delete the whole folder when a project does not need it.

It has no authentication. Never expose it outside a developer machine or CI.

## Where each file type goes

Paths are relative to `blueprints/bookmarks/`.

| What                                                                                 | Where                                                                |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| `HttpApi`, wire schemas (shared by server and web)                                   | `packages/contract`                                                  |
| Value objects, the aggregate, `MAX_TAGS`, domain errors                              | `packages/domain`                                                    |
| Ports, use cases, DTOs, port errors, test fakes                                      | `packages/application` (`src/ports`, `src/use-cases`, `src/testing`) |
| Repositories (SQL, in memory), ids, rows, migrations                                 | `packages/infrastructure` (`src/migrations/<id>_<name>.ts`)          |
| HTTP handlers, problems, health, acceptance suite                                    | `packages/api` (`*.handlers.ts`, `src/testing`)                      |
| Composition root: `main.ts`, `main.memory.ts`, `migrate.ts`, `seed.ts`, `openapi.ts` | `apps/server/src`                                                    |
| Published contract (generated)                                                       | `apps/server/api/openapi.json`                                       |
| React + Vite web app                                                                 | `apps/web`                                                           |
| Container images (`Dockerfile`, nginx template)                                      | `apps/server`, `apps/web` (`nginx/`)                                 |

Shared code lives at the repository root: `packages/backend-shared`,
`packages/contracts/problem-details` and, for the web app, the design system in `packages/design`.
`pnpm ports:check` checks ports and adapters against ADR 0003 and ADR 0006.

## Build a new service from it

The blueprint is a reference, not a copy source: a new project usually deletes it. Write the
service's spec first (`specs/NNN-slug/`), then build `packages/<service>/` and
`apps/<service>-server` (and `apps/<service>-web`, if needed) in the same shapes:

- the layers and the file placement of the table above, with packages named `@pocket-comms/<service>-…`,
  the `scope:<service>` tag, service keys `<service>/application/…` and the service's own schema;
- the local dev targets below, so that `pnpm dev` starts the service too.

Then run `pnpm install`, `pnpm nx sync` and `pnpm format`, then `pnpm verify:local`.

The web app is the frontend Golden Path: it depends only on the contract and `@pocket-comms/design-ui`,
calls the API through `HttpApiClient` (ADR 0008), routes and caches with TanStack Router and
TanStack Query (ADR 0011), and builds its page from the UI kit, with no stylesheet or inline style
of its own (ADR 0009). A new web app copies these shapes from `apps/web`:

| File                                     | Holds                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| `src/<service>-client.ts`                | The typed client as plain promises; the only code that calls the API     |
| `src/<service>-queries.ts`               | Query keys and `queryOptions` factories whose `queryFn` calls the client |
| `src/routes/`                            | One file per address; `__root.tsx` renders an `Outlet`                   |
| `src/routeTree.gen.ts`                   | Generated by the Vite plugin; never edit, commit it                      |
| `src/router-context.ts`, `src/router.ts` | The client in the router context; `createAppRouter({ client, history })` |
| `src/main.tsx`                           | One `QueryClient`, the router inside `QueryClientProvider`               |
| `src/testing.tsx`                        | A fake client and `renderApp`, which renders a route via memory history  |
| `tsr.config.json`, `vite.config.ts`      | Route generation; `tanstackRouter()` before `react()`                    |

A route reads the client with `Route.useRouteContext()`. A mutation calls the client and, on
success, invalidates the query keys it changes. After adding or renaming a route file, run
`pnpm exec tsr generate` in the app (or start `dev`) and commit the tree; `routes-check` fails on
a stale one. Give the app's `project.json` the same `routes-check` target, with `lint` depending
on it.

## Run it locally

From the repository root, `pnpm dev` starts PostgreSQL 17, migrates, adds the example bookmarks,
then runs the API on `:3001` and the web app on `:4200` (it proxies `/api` to `:3001`). Ctrl+C
stops the API and the web app; PostgreSQL keeps running with its data. The Nx targets behind it:

| Target                                  | Does                                                                         |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| `bookmarks-web:dev`                     | Vite, after `bookmarks-server:dev`                                           |
| `bookmarks-server:dev`                  | the API, rebuilt and restarted on change, after `seed-dev`                   |
| `bookmarks-server:seed-dev`             | adds the examples of `src/examples.ts` that are missing, after `migrate-dev` |
| `bookmarks-server:migrate-dev`          | the migrations, after `db-up`                                                |
| `bookmarks-server:db-up`                | checks Docker, then `docker compose up --wait`                               |
| `bookmarks-server:db-down` / `db-reset` | `docker compose down`, keeping the data / `down -v`, wiping it               |
| `bookmarks-{web,server}:dev-memory`     | the same app on the in-memory adapters (`main.memory.ts`), no Docker         |

The root scripts run these targets for every app: `pnpm dev`, `pnpm dev:memory`, `pnpm dev:down`
and `pnpm dev:reset`. The seed goes through the use cases and skips a URL that is taken, so every
start is safe; an example you delete comes back on the next start. For the web app alone, against
another API, run `API_URL=<url> pnpm nx run bookmarks-web:dev --exclude-task-dependencies`. On
Podman, `docker` must be the Podman alias.

The dev targets and the `local` configurations hold development credentials only. Elsewhere
`serve` and `migrate` read `DATABASE_URL` (a secret) and `PORT` (default 3000). The server serves
`/api/v1`, `/docs/openapi.json`, a browser UI at `/docs`, `/health/live` and `/health/ready`.

## Container images

Both images build from the repository root and run as non-root users. The `.dockerignore` file
leaves out `node_modules` and `dist`, so each image builds from source:

```bash
docker build -f blueprints/bookmarks/apps/server/Dockerfile -t bookmarks-server .
docker build -f blueprints/bookmarks/apps/web/Dockerfile -t bookmarks-web .
```

- `bookmarks-server` runs `dist/main.js`. Run `node --enable-source-maps dist/migrate.js` once
  before it, as a one-shot container from the same image. Both read `DATABASE_URL` and `PORT`.
- `bookmarks-web` is nginx on port 8080. It serves the app and proxies `/api`, `/docs` and
  `/health` to `BOOKMARKS_SERVER_HOST:BOOKMARKS_SERVER_PORT` (default `bookmarks-server:3000`).
  It resolves that name per request, so it starts without the server and follows a recreated
  server container.
- `pnpm deploy --legacy` builds the server's `node_modules`, because the workspace does not
  inject its packages. A new runtime dependency needs no Dockerfile change.
- Pull requests build both images without pushing them (the `images` job in `ci.yml`). A tag
  `bookmarks-vX.Y.Z` runs `.github/workflows/release.yml`, which pushes both images as `X.Y.Z` to
  `$REGISTRY_HOST/<owner>/bookmarks-{server,web}`. It needs the Actions variable `REGISTRY_HOST`
  and the Actions secret `REGISTRY_TOKEN`. A release needs the owner's approval.

## Test it

- `pnpm nx run-many -t test` runs every test. Repository, migration and runtime tests start
  PostgreSQL with Testcontainers and need Docker. On Podman, set
  `TESTCONTAINERS_RYUK_DISABLED=true`.
- A new use case gets tests in `packages/application` with the fakes; a new endpoint gets cases in
  `packages/api/src/testing/acceptance.ts`; a new repository behaviour gets a case in the
  repository contract suite, which both adapters run.

## Observability

The server exports traces, metrics and logs over OTLP with Effect's built-in exporter (ADR 0010).
`composition.ts` serves the API with `Observability.serve(…, { serviceName: 'bookmarks-server' })`
from `@pocket-comms/backend-shared/observability`, in place of `HttpRouter.serve`. When you copy the
server, rename the service name; nothing else changes. Only server composition roots may import
the module (`observability-in-servers-only`).

Each signal is off until its endpoint is set, so tests and local runs need no backend:

| Variable                              | Effect                                                   |
| ------------------------------------- | -------------------------------------------------------- |
| `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` | Metrics to this URL as given                             |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`  | Traces to this URL as given                              |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`    | Logs to this URL as given                                |
| `OTEL_EXPORTER_OTLP_ENDPOINT`         | Base for every signal without its own variable (`/v1/…`) |
| `OTEL_SERVICE_NAME`                   | Overrides the service name                               |
| `OTEL_RESOURCE_ATTRIBUTES`            | `service.version`, `deployment.environment.name`, …      |

The homelab's backend (smotastic/pocket-cloud#3) is Prometheus, which receives metrics only: set
`OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://<prometheus>:9090/api/v1/otlp/v1/metrics`. The
metric is `http.server.request.duration` (seconds) by method, route pattern and status code.
Health checks are counted but not traced. Tests read spans, logs and metrics from the recording
kit in `@pocket-comms/backend-shared/observability/testing` (`observability.spec.ts`).

## Migrations

- Add `<4 digits>_<snake_case>.ts` in `packages/infrastructure/src/migrations/` with a higher id
  and register it in the migrator's record. ADR 0004 holds the rules; every migration needs the
  owner's approval.
- Never change or delete a merged migration.
- `runMigrations` takes an advisory lock and creates the schema and migrations table before the
  `Migrator` runs, so two first-time runners never race. Keep this in a new service.

## Contracts

After a change to the contract, run `pnpm nx run bookmarks-server:openapi` and commit the
document. `pnpm openapi:check`, `pnpm openapi:lint` and `pnpm openapi:diff` fail on a stale
document, a missing description or example, or a breaking change against `master`.
